     Procedural Case Generation System - Design Plan

     Overview

     A Dwarf Fortress-inspired simulation system that generates organic 
     police cases through emergent behavior. Actors with needs/desires live
     their lives, accumulate grievances, and eventually commit crimes when
     conditions align.

     Architecture: 8-Phase Pipeline

     Each phase produces output that the next phase consumes (DF-style 
     layered generation).

     ┌─────────────┐    ┌─────────────┐    ┌─────────────┐    
     ┌─────────────┐
     │ Foundation  │ -> │ Population  │ -> │ Simulation  │ -> │   Crime     
     │
     │   Phase     │    │   Phase     │    │   Phase     │    │  Emergence  
     │
     └─────────────┘    └─────────────┘    └─────────────┘    
     └─────────────┘
                                                                     │
     ┌─────────────┐    ┌─────────────┐    ┌─────────────┐           │
     │    Blank    │ <- │    Case     │ <- │  Evidence   │ <- │ Crime      │
     │ Generation  │    │ Extraction  │    │ Generation  │    │ Selection  │
     └─────────────┘    └─────────────┘    └─────────────┘    
     └─────────────┘

     ---
     Phase 1: Foundation

     Purpose: Create the physical world - locations where events can occur.

     Outputs:
     - Districts (3-8 based on city size)
     - Locations within districts (homes, workplaces, public spaces)
     - Location properties (type, capacity, hours, security level)

     SQLite Tables:
     CREATE TABLE districts (
         id INTEGER PRIMARY KEY,
         name TEXT,
         wealth_level INTEGER,      -- 1-5
         crime_rate INTEGER         -- 1-5
     );

     CREATE TABLE locations (
         id INTEGER PRIMARY KEY,
         district_id INTEGER,
         name TEXT,
         type TEXT,                 -- home, office, bar, warehouse, bank, 
     etc.
         is_public INTEGER,
         open_hour INTEGER,
         close_hour INTEGER,
         security_level INTEGER,    -- 0=none, 1=cameras, 2=guards, 3=vault
         capacity INTEGER
     );

     ---
     Phase 2: Population

     Purpose: Generate actors with personalities, needs, and pre-existing 
     relationships.

     Actor Attributes:
     - Demographics: name, age, sex
     - Personality (0-100 each): impulsivity, morality, greed, aggression, 
     loyalty
     - Needs (0-100 each): money, belonging, status, security, comfort
     - Occupation + income level
     - Home location, workplace location

     Relationships (pre-generated):
     - Family (spouse, sibling, parent/child)
     - Professional (boss, coworker, employee)
     - Social (friend, acquaintance, rival)
     - Romantic (partner, ex, affair)

     SQLite Tables:
     CREATE TABLE actors (
         id INTEGER PRIMARY KEY,
         name TEXT,
         age INTEGER,
         sex TEXT,
         occupation TEXT,
         income INTEGER,
         home_id INTEGER,
         work_id INTEGER,
         -- Personality traits
         impulsivity INTEGER,
         morality INTEGER,
         greed INTEGER,
         aggression INTEGER,
         loyalty INTEGER,
         -- Current need levels (updated during simulation)
         need_money INTEGER,
         need_belonging INTEGER,
         need_status INTEGER,
         need_security INTEGER
     );

     CREATE TABLE relationships (
         id INTEGER PRIMARY KEY,
         actor1_id INTEGER,
         actor2_id INTEGER,
         type TEXT,                 -- family, friend, coworker, rival, 
     romantic
         subtype TEXT,              -- spouse, sibling, boss, ex, etc.
         strength INTEGER,          -- 1-100
         sentiment INTEGER          -- -100 to +100 (hate to love)
     );

     ---
     Phase 3: Simulation (Core Loop)

     Purpose: Advance time, actors make decisions based on needs, events 
     accumulate.

     Time Model:
     - Simulate hour-by-hour for 60-90 days
     - Each actor has a daily routine (wake, work, leisure, sleep)
     - Decisions made at each "decision point" in the day

     Need Decay & Satisfaction:
     - Needs decay over time (money decreases, belonging fades without 
     social contact)
     - Activities satisfy needs (work → money, socializing → belonging)
     - Unmet needs cause stress, affect decisions

     Event System:
     All significant occurrences logged to events table:
     - Routine events: arrive_work, leave_work, go_home
     - Social events: conversation, argument, insult, favor, betrayal
     - Economic events: paid, spent, borrowed, fired, promoted
     - Conflict events: witnessed_crime, threatened, attacked

     Grievance Accumulation:
     When negative events occur, grievances form:
     CREATE TABLE grievances (
         id INTEGER PRIMARY KEY,
         victim_id INTEGER,         -- Who was wronged
         offender_id INTEGER,       -- Who wronged them
         cause_event_id INTEGER,    -- The triggering event
         severity INTEGER,          -- 1-100
         timestamp INTEGER,
         resolved INTEGER DEFAULT 0
     );

     Decision Logic (per actor per decision point):
     1. Evaluate current needs (which are low?)
     2. Consider available actions at current location/time
     3. Weight actions by: need satisfaction + personality + relationships
     4. Select action (with some randomness based on impulsivity)
     5. Execute action, log event, update needs

     SQLite Tables:
     CREATE TABLE events (
         id INTEGER PRIMARY KEY,
         timestamp INTEGER,         -- Simulation hour (0 = day 1 hour 0)
         event_type TEXT,
         actor_id INTEGER,
         target_id INTEGER,         -- Other actor involved (if any)
         location_id INTEGER,
         details TEXT               -- JSON for extra data
     );

     CREATE TABLE actor_states (
         id INTEGER PRIMARY KEY,
         timestamp INTEGER,
         actor_id INTEGER,
         location_id INTEGER,
         activity TEXT,
         need_money INTEGER,
         need_belonging INTEGER,
         need_status INTEGER,
         need_security INTEGER
     );

     ---
     Phase 4: Crime Emergence

     Purpose: Detect when conditions align for a crime to occur.

     Crime Potential Formula:
     For each actor A, for each potential victim V:

     motive = weighted_sum(
         unmet_needs(A),
         grievance_severity(A → V),
         potential_gain(crime_type, V)
     )

     opportunity = calculate(
         access_to_victim(A, V, time),
         witness_probability(location, time),
         victim_vulnerability(V)
     )

     capability = has_means(A, crime_type)

     inhibition = A.morality * fear_factor(crime_type) * 
     relationship_weight(A, V)

     crime_score = (motive + opportunity + capability) - inhibition

     if crime_score > THRESHOLD:
         trigger_crime(A, V, select_crime_type())

     Crime Types & Requirements:

     | Crime  | Motive Drivers                          | Opportunity Needs 
                     | Capability                |
     |--------|-----------------------------------------|-------------------
     ----------------|---------------------------|
     | Murder | Grievance, Inheritance, Silence witness | Private location, 
     No witnesses    | Weapon or strength        |
     | Kidnap | Money (ransom), Control, Revenge        | Isolated moment, 
     Transport        | Accomplice or strength    |
     | Theft  | Money need, Greed                       | Access to 
     valuables, Low security | Tools or inside knowledge |

     Crime Planning:
     When crime_score crosses threshold, don't execute immediately:
     1. Actor enters "planning" state
     2. Over next 1-7 days, actor makes preparations (logged as events)
     3. Actor waits for optimal opportunity
     4. Crime executes, full event chain logged

     ---
     Phase 5: Crime Selection

     Purpose: After simulation ends, grade all crimes and pick the most 
     interesting.

     Grading Criteria:
     interest_score = (
         causality_chain_length * 2.0 +    -- Longer chains more interesting
         num_suspects * 1.5 +               -- More suspects = more 
     investigation
         evidence_variety * 1.5 +           -- Different evidence types
         red_herring_potential * 1.0 +      -- Other actors with motive
         relationship_complexity * 1.0      -- Connected actors
     )

     Selection:
     - Rank all crimes by interest_score
     - Select top crime (or allow selection from top 3)

     ---
     Phase 6: Evidence Generation

     Purpose: Determine what traces the crime left behind.

     Evidence Types:

     | Category    | Examples                                 | Generation 
     Rules                                      |
     |-------------|------------------------------------------|-------------
     ------------------------------------------|
     | Physical    | Weapon, fingerprints, DNA, fibers        | Based on 
     location, crime type, perpetrator care level |
     | Testimonial | Witness statements                       | Based on who
      was at/near location at time             |
     | Documentary | Receipts, records, photos, video         | Based on 
     location security level, actor activities    |
     | Digital     | Phone records, emails, bank transactions | Based on 
     actor actions during planning/execution      |

     Evidence Quality:
     - Each piece has a clarity score (1-100)
     - Affected by: perpetrator impulsivity (rushed = more evidence), 
     location security, time of day

     Witness Generation:
     CREATE TABLE witnesses (
         id INTEGER PRIMARY KEY,
         crime_id INTEGER,
         actor_id INTEGER,
         saw_what TEXT,             -- What they observed
         reliability INTEGER,       -- How accurate (affected by conditions)
         willingness INTEGER        -- How cooperative
     );

     ---
     Phase 7: Case Extraction

     Purpose: Build the complete case file from simulation data.

     Causality Chain Construction:
     1. Start from crime event
     2. Trace back: what event enabled this?
     3. Repeat until reaching "root cause" or chain length 3-7
     4. Each link: (event, actor, location, time, why_it_matters)

     Output Structure (JSON):
     {
       "crime": {
         "type": "murder",
         "perpetrator_id": 42,
         "victim_id": 17,
         "timestamp": 1847,
         "location_id": 23
       },
       "causality_chain": [
         {"event_id": 1201, "summary": "Victim fired perpetrator", "day": 
     15},
         {"event_id": 1456, "summary": "Perpetrator's savings depleted", 
     "day": 31},
         {"event_id": 1678, "summary": "Perpetrator overheard victim mocking
      them", "day": 45},
         {"event_id": 1890, "summary": "Perpetrator acquired weapon", "day":
      52},
         {"event_id": 1923, "summary": "Murder committed", "day": 58}
       ],
       "suspects": [...],
       "witnesses": [...],
       "evidence": [...],
       "alibis": [...],
       "red_herrings": [...]
     }

     ---
     Phase 8: Blank Generation

     Purpose: Select what to hide from the player; ensure solvability.

     Blank Categories:
     - WHO: Actor identity (perpetrator, accomplice, witness)
     - WHERE: Location of event
     - WHEN: Time of event
     - WHAT: Object involved (weapon, vehicle, document)

     Solvability Rules:
     For each blank B:
       evidence_count = count(evidence that reveals B)
       if evidence_count < 1:
         skip this blank (not solvable)
       if evidence_count >= 2:
         mark as good blank candidate

     Red Herring Integration:
     - Other suspects with motive but solid alibis
     - Evidence that points to wrong actor
     - Misleading witness statements (honest mistakes or lies)

     ---
     File Structure

     cc-casegen/
